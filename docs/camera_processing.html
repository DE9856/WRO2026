§01

System Philosophy — Why Not Deep Learning?

Many beginners attempt to train a CNN to directly map camera frames to steering commands. While elegant in theory, this approach fails in practice on a Raspberry Pi 4B under WRO competition conditions. The architecture chosen here is engineered vision augmented with lightweight intelligence — the same paradigm used in real ADAS systems.

❌ Naive Deep Learning

Camera → CNN → Steering angle. Requires massive datasets, GPU-grade hardware, produces black-box decisions, latency of 30–120 ms per frame, impossible to debug at competition.

✅ This System

Engineered geometry + lightweight ML optimization. Deterministic, debuggable, sub-5 ms core loop, no dataset required, mirrors professional ADAS design philosophy.

💡
WRO Competition Alignment

The rules explicitly reward "use of computer vision and sensor fusion to estimate the state of the parkours." A geometry-driven pipeline with explainable state vectors scores better on the engineering journal (Criterion 3 — Software Architecture) than a black-box CNN that the team cannot fully explain.

§03

Camera Hardware & Configuration

The vision system supports two interchangeable camera options: a Logitech C270 USB webcam (current default hardware, connected via cv2.VideoCapture over UVC) and a Raspberry Pi Camera Module (Rev 1.3 or V2, connected via CSI ribbon cable and accessed through picamera2). Everything downstream of frame capture — ROI crop, HSV masking, contour detection, distance/angle estimation — operates on the same BGR numpy array regardless of which camera produced it, so the two are drop-in alternatives for each other at the capture layer only.

⚠️
Current hardware vs. supported alternative

The C270 is what's actually mounted on the vehicle today (see BOM in hardware.html) — it replaced an originally-planned Pi Camera Module V2 so the capture code wouldn't be tied to a Pi-specific API. The Pi Camera path below is kept fully documented and supported as a fallback/alternative, not a leftover: swap hardware, swap the capture function, and the rest of the pipeline is unaffected. Whichever camera is physically installed, its FOV must be measured and locked into camera/angle.py::CAMERA_FOV before relying on any distance estimate.

Capture Code — Both Options

The two capture functions below return an identical BGR frame shape, so a single capture.py can select between them with one config flag (e.g. --camera {c270,picam}) without touching anything downstream.

Python — Logitech C270 (OpenCV VideoCapture) 
import cv2

cap = cv2.VideoCapture(0)  # /dev/video0 — confirm index if other UVC devices are attached
cap.set(cv2.CAP_PROP_FRAME_WIDTH,  640)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 480)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*"MJPG"))
cap.set(cv2.CAP_PROP_FPS, 30)
cap.set(cv2.CAP_PROP_AUTO_EXPOSURE, 1)   # 1 = manual mode on most UVC drivers
cap.set(cv2.CAP_PROP_EXPOSURE, -6)       # fixed exposure step — tune on-site

# Main loop
while True:
    ok, frame = cap.read()  # BGR np.ndarray, ~640x480x3
    if not ok:
        continue
    # → pass to ROI crop next
Python — Raspberry Pi Camera Module (picamera2) 
from picamera2 import Picamera2
import cv2

picam2 = Picamera2()
config = picam2.create_preview_configuration(
    main={"size": (640, 480), "format": "BGR888"},
    controls={
        "ExposureTime": 8000,      # µs — freeze exposure
        "AnalogueGain": 2.0,       # fixed gain
        "AwbEnable": False,         # disable auto white balance
        "ColourGains": (1.4, 1.5), # manual WB (tune on-site)
    }
)
picam2.configure(config)
picam2.start()

# Main loop
while True:
    frame = picam2.capture_array()   # ~2–4 ms capture time, same BGR shape as VideoCapture
    # → pass to ROI crop next
🔁
Swapping cameras mid-season

Because both paths hand off an identical frame shape, switching hardware only means re-running HSV calibration and re-measuring CAMERA_FOV — no changes needed in camera/warp.py, camera/corridor.py, or any contour/distance code past the capture step.

§04

Region of Interest (ROI) Processing

ADAS systems never process entire frames uniformly. The robot needs to see only the road region ahead — specifically the lower-center area where pillars appear at competition-relevant distances. ROI cropping is the single most impactful optimization available.

📈
FPS Impact of ROI

Processing a 640×280 ROI instead of 640×480 reduces pixel count by 42%, translating directly to a proportional reduction in HSV conversion and morphological operation time. Observed FPS improvement: ~35–50% on Pi 4B.

ROI Definition Strategy

The ROI should capture the zone from the horizon down to the front bumper of the robot. Experimentally determine y_start by placing a pillar at maximum detection range and noting its lowest visible pixel row.

Python — ROI Crop 
# Full frame: 640 × 480
# ROI: rows 200–460, cols 80–560 (tune to your camera mount)

def extract_roi(frame):
    roi = frame[200:460, 80:560]   # y_start:y_end, x_start:x_end
    return roi

# Optional: downscale the ROI further for extreme speed
def extract_roi_fast(frame):
    roi = frame[200:460, 80:560]
    return cv2.resize(roi, (320, 130))  # halved — very fast

# Visualize ROI during tuning (remove for competition)
cv2.rectangle(frame, (80, 200), (560, 460), (0, 255, 255), 2)

Why not the whole frame?

Upper region (sky / ceiling)

Contains no pillars, no walls, no useful data. Only contributes noise and wasted CPU cycles. Always discard.

Far edges (left/right extremes)

At 640 px wide, edge pillars are near-wall and already committed passes. Crop to ~80–560 to center on actionable geometry.

§04A

Bird's Eye Perspective Transformation

Raw camera frames suffer from perspective distortion. Objects farther away appear smaller and skewed, making geometric reasoning inconsistent. Modern ADAS systems solve this using a Bird’s Eye Perspective Transform.

The camera frame is warped into a top-down geometric representation of the field. This stabilizes obstacle positions, improves ROI consistency, simplifies seat localization, and dramatically improves state estimation reliability.

🛰️
Why This Matters

After perspective correction, the robot no longer reasons in distorted image space. It reasons in a geometry-stabilized field representation similar to real autonomous vehicles.

Perspective Warp Using OpenCV

Python — Bird's Eye Warp 
import cv2
import numpy as np

# Source points from camera image
src = np.float32([
    [120, 320],
    [520, 320],
    [0,   480],
    [640, 480]
])

# Destination points for top-down view
dst = np.float32([
    [160, 0],
    [480, 0],
    [160, 480],
    [480, 480]
])

# Compute transformation matrix
M = cv2.getPerspectiveTransform(src, dst)

# Apply perspective warp
warped = cv2.warpPerspective(
    frame,
    M,
    (640, 480)
)

Advantages of Bird’s Eye Geometry

Without Warp

Strong perspective distortion, inconsistent obstacle scaling, unstable seat geometry, poor localization accuracy.

With Warp

Stable geometric reasoning, predictable seat indexing, improved obstacle consistency, better trajectory planning.

📍
Critical for Configuration Matching

Perspective normalization is one of the key enabling technologies behind reliable seat-state encoding and constrained-state reasoning.

§05

HSV Color Segmentation

RGB color detection is notoriously unstable under varying lighting — a red pillar under fluorescent competition lights will have a completely different RGB value than under daylight. HSV (Hue-Saturation-Value) separates color identity from brightness, making masks robust to illumination changes.

ChannelMeaningRangeWhy It Matters
H (Hue)Pure color identity0–179 in OpenCVStable under brightness changes
S (Saturation)Color purity / vividness0–255Filters grey walls, floor, shadows
V (Value)Brightness0–255Lower bound prevents black noise matches

WRO Official Pillar Colors → HSV Masks

The rules specify exact RGB values for traffic signs (§13.21, §13.22) and parking markers (§13.27). These translate to the following HSV thresholds:

RGB (238, 39, 55) — Rule §13.21
Green Pillar
RGB (68, 214, 44) — Rule §13.22
Magenta Marker

Python — HSV Masks (all three objects) 
import numpy as np
import cv2

def build_masks(roi):
    hsv = cv2.cvtColor(roi, cv2.COLOR_BGR2HSV)

    # ── RED PILLAR (wraps around hue 0°) ──────────────────────────
    # Red spans two ranges in OpenCV HSV (0–10 and 170–180)
    lower_red1 = np.array([0,  120, 70])
    upper_red1 = np.array([10, 255, 255])
    lower_red2 = np.array([170, 120, 70])
    upper_red2 = np.array([180, 255, 255])

    mask_red = (cv2.inRange(hsv, lower_red1, upper_red1) |
                cv2.inRange(hsv, lower_red2, upper_red2))

    # ── GREEN PILLAR ──────────────────────────────────────────────
    lower_green = np.array([40,  50,  50])
    upper_green = np.array([90, 255, 255])
    mask_green  = cv2.inRange(hsv, lower_green, upper_green)

    # ── MAGENTA PARKING MARKERS ───────────────────────────────────
    lower_mag  = np.array([140, 80, 80])
    upper_mag  = np.array([170, 255, 255])
    mask_mag   = cv2.inRange(hsv, lower_mag, upper_mag)

    return mask_red, mask_green, mask_mag
⚠️
Tune on the Actual Field

The specified RGB values are print targets; actual pillar colors vary by manufacturer and lighting. Use cv2.createTrackbar() during practice time to adjust thresholds live. Save final values as constants — never hard-code without field validation.

§06

Morphological Operations

Raw HSV masks are noisy — reflections off shiny pillars, light spill on white floor, and JPEG compression artifacts create thousands of false positive pixels. Morphological operations clean up the binary mask using structuring elements (kernels).

OperationEffectUse CaseOpenCV Call
ErosionShrinks white regionsKill tiny noise blobscv2.erode()
DilationGrows white regionsFill gaps in pillar maskcv2.dilate()
OpeningErode then DilateRemove isolated salt noiseMORPH_OPEN
ClosingDilate then ErodeFill holes inside pillarMORPH_CLOSE
Python — Morphological Cleanup 
def clean_mask(mask, kernel_size=5):
    k = cv2.getStructuringElement(
        cv2.MORPH_RECT, (kernel_size, kernel_size)
    )
    # Step 1: Opening — eliminate salt-and-pepper noise
    mask = cv2.morphologyEx(mask, cv2.MORPH_OPEN,  k)
    # Step 2: Closing — seal internal holes in pillar blob
    mask = cv2.morphologyEx(mask, cv2.MORPH_CLOSE, k)
    return mask

# Larger kernel = more aggressive cleaning, but risks eating thin detections
# Recommended: kernel_size 3 (fast), 5 (balanced), 7 (heavy noise)
§07

Contour Detection & Bounding Boxes

After cleaning the mask, contour detection extracts the mathematical boundaries of each blob. From the contours we derive all geometric properties needed for distance and angle estimation.

Python — Full Contour Pipeline 
def detect_objects(mask, min_area=300, label="unknown"):
    contours, _ = cv2.findContours(
        mask,
        cv2.RETR_EXTERNAL,       # only outer boundaries
        cv2.CHAIN_APPROX_SIMPLE  # compress to corners only (faster)
    )

    objects = []
    for cnt in contours:
        area = cv2.contourArea(cnt)
        if area < min_area:
            continue  # filter out micro-noise

        x, y, w, h = cv2.boundingRect(cnt)
        cx = x + w // 2         # horizontal center
        cy = y + h // 2         # vertical center
        aspect = w / (h + 1e-6) # pillar should be ~0.5 (tall)

        # Reject wide blobs (likely floor reflections, not pillars)
        if aspect > 2.5:
            continue

        objects.append({
            "label":  label,
            "x": x, "y": y, "w": w, "h": h,
            "cx": cx, "cy": cy,
            "area": area,
            "aspect": aspect,
        })

    # Return largest object first (closest pillar = largest bbox)
    return sorted(objects, key=lambda o: o["area"], reverse=True)
